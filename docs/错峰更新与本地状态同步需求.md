### 0.2 本次要解决的三个真实缺陷

1. **一轮 = 一次性 burst**：`RssTask.download(...)` 把全部启用订阅一次性 `submit` 进 `newFixedThreadPool(rssConcurrency)`（默认 3，上限 `MAX_ANI_PARALLELISM = 8`），提交间只有 `ThreadUtil.sleep(50)`（注释自称"轻抖动错峰"）。订阅 80 个时仍会在极短时间内产生 80 次 RSS 拉取 + 80 次网盘列举。
2. **轮次与改名完全无协调**：`RssTask.accept` 每 `rssSleepMinutes`（默认 15）无条件开一轮；`RenameTask` 每 `renameSleepSeconds`（默认 10）独立跑一轮。下载完成但尚未改名的窗口内，真实文件校验会得出"本地不存在" → **触发重复下载**。这是本需求最关键的回归点。
3. **每个入口各扫各的**：预览、媒体库、RSS 主流程、手动搜索各自构建集数索引，互相不复用，网盘调用数被放大数倍。

### F2 结果缓存（订阅级本地状态快照）

**现状**：四处缓存各自为政；同一轮内同一订阅被多次构建索引。

**落地状态（2026-09-16）**：F2-1 ~ F2-8 **全部完成**。
新增 `ani.rss.service.LocalStateCache`（静态 LRU + TTL + 单飞 + 版本化失效）。
`DownloadService.prepareLocalState` 与 `itemDownloaded` 均改为经 `cachedEpisodeIndex(...)` 走缓存，
预览 / 媒体库 / 手动搜索 / RSS 主流程因此共用同一份索引。
失效钩子已接：`DownloadService.invalidateDownloadPathIndex()`（被 `AniUtil.sync()` 与
`ConfigUtil.syncChecked()` 调用 → 覆盖订阅增删改与模板变更）、`TorrentUtil.rename` 成功后
（按下载目录精确失效）、`TorrentUtil.promoteTorrent`、`forceDownloadItem`、`restoreTorrentRecord`、
`TorrentController.deleteTorrent`。
验收：`ani.rss.service.LocalStateCacheTest`（18 项）。

**需求**

| 编号 | 要求 | 落地方式 |
|---|---|---|
| F2-1 ✅ | 新增订阅级快照缓存 | `ani.rss.service.LocalStateCache`（静态 `ConcurrentHashMap` + `CompletableFuture` 单飞） |
| F2-2 ✅ | 缓存内容 | `key = ani.id + "\|" + sha1(downloadPath)`；`value = { Set<String> episodeIndex, Source source, long builtAt, boolean complete }`；`Source ∈ {LOCAL_DISK, CLOUD_API}` |
| F2-3 ✅ | 分级 TTL | 本地磁盘 `60_000ms`；网盘 `300_000ms`；由 `Config.localStateCacheTtlSeconds`（10–3600）/ `cloudStateCacheTtlSeconds`（30–3600）覆盖 |
| F2-4 ✅ | 单飞（single-flight） | `ConcurrentHashMap<String, CompletableFuture<Snapshot>>`，`finally` 中移除；等待方有 30s 上限，超时按"校验失败"处理（→ 存疑），绝不无限期挂起 |
| F2-5 ✅ | 容量上限 | `max(64, 订阅数 × 2)`，超出时按 `builtAt` 淘汰最旧 |
| F2-6 ✅ | 失效钩子 | 见上方"落地状态"；`invalidate(aniId)` / `invalidateByDownloadPath(path)` / `invalidateAll()` 三种粒度 |
| F2-7 ✅ | 复用范围 | `previewAni` / `LibraryController.scanOne` / `itemDownloaded` / `ManualSearchController` 全部经缓存 |
| F2-8 ✅ | 不落盘 | 纯内存，无任何序列化；重启后从空开始 |

> **实现补充**：失效与构建的竞态用**版本号**解决——构建开始时记下订阅版本 + 路径版本 + 全局世代，
> 构建结束时三者任一变化即丢弃结果不写回。没有这一步，"失效"会被一个更早开始、更晚结束的
> 旧构建覆盖掉（用户刚下完刷新却仍看到旧结果）。
>
> **`invalidateByDownloadPath` 存在的理由**：改名完成事件只拿得到"下载目录"，拿不到订阅 id
> （下载器任务上不带订阅信息）。若只能按订阅失效，就只能退化成"整体失效"，
> 而一轮里每下完一集都会整体清空一次缓存，缓存等于没有。

### F4 后处理完成后才触发下一轮（静默窗口）

> **实现时的核实结论（与 §0.2 缺陷 2 的差异）**：`downloadAni` 的第一道闸门是按 **infoHash**
> 比对下载器任务（`DownloadService:376-386`），它在整个改名窗口内都成立，所以"未改名即重复下载"
> 并非必然发生；真正裸露的是**该任务已从下载器移除、而文件尚未改名**这一更窄的窗口，
> 以及 `rename=true && fileExist=true` 下走真实文件索引的那条路径。
> 因此 F4 的定位是**消除竞态窗口的加固**（把"零协调"变成"显式等待"），而非修复一个必现 bug。

### F5 旧逻辑先行 + 统一标"存疑"（两阶段收敛）

**现状**：预览一次性用真实文件判定，得到 是 / 存疑 / 否（存疑仅作兜底）。

**落地状态（2026-09-16）**：F5-2 / F5-4 / F5-5 / F5-6 完成；F5-1 / F5-3 为"固化现状"（无需改动）。
Phase A / Phase B 的**显式阶段对象**未引入——三态判定入口 `resolveLocalState(...)` 已按
"记录 → 文件"的优先级实现同一语义，阶段边界由 F4 的静默窗口承担。
- F5-2：`DownloadService.countStaleTorrentRecords(items)` 统计"有记录但文件已确认不在"的条目，
  预览页给出「记录与文件不一致 N 项」提示；**只提示不删记录**（记录是"曾经下过"的唯一线索）。
- F5-6：本轮分布 `RssTask.getRoundLocalStateSummary()` → `RssJobStatus.roundLocalState`
  → 任务管理器「本地状态：已存在 x · 无法确认 y · 已下发 z」。语义是**本轮处置结果**，
  与展示层三态区分（`EXISTS`=跳过下载，`UNKNOWN`=无法确认跳过，`ABSENT`=已下发）。
- 验收：`ani.rss.service.PreviewLocalExistsTest`（含不一致计数）、
  `ani.rss.task.RoundLocalStateSummaryTest`（3 项）。

**需求**：把判定拆成**显式两阶段**，阶段边界与 F4 的静默窗口对齐。

| 阶段 | 触发时机 | 判据 | 网盘调用 | 产出 | 允许的写动作 |
|---|---|---|---|---|---|
| **Phase A 快照** | 每轮 RSS 更新开始、错峰批次提交前 | **既有旧逻辑**：`TorrentUtil.getTorrent(ani, item).exists()`（本地 `.torrent` 记录） | **0** | 记录存在 → `UNKNOWN`；记录不存在 → `ABSENT` | 无（不补记录、不删记录、不下发下载） |
| **Phase B 确认** | 该订阅处于静默（F4）且 API 预算允许 | `DownloadService.itemFileExists(ani, item, index)`，索引来自 F2 缓存（严格版列举） | ≤1 次/订阅/轮 | 真实存在 → `EXISTS` + 补回种子记录；确认不存在 → `ABSENT`；**校验失败 / 超预算 / 索引不完整 → 保持 `UNKNOWN`** | 仅在 `EXISTS` 且记录缺失时 `restoreTorrentRecord` |

**硬性约束**

- F5-1：Phase A 的 `UNKNOWN` **绝不可**被下游当作"否"。`DownloadService.itemDownloaded`（下载去重）继续走"非严格 + 保守重下"，本次**不改其判定逻辑**。
- F5-2：Phase B 判出 `ABSENT` 时**不删种子记录**，只在任务管理器给"记录与文件不一致，可清理"提示（沿用 `FailedDownloadQueue` / 失败明细的呈现方式）。
- F5-3：`rename=false`（文件名不可预测，按集数匹配无从谈起）→ **不发起任何网盘调用**，直接按本地种子记录判定：有记录 → `EXISTS`，无记录 → `ABSENT`。**该分支不产生 `UNKNOWN`**（已实现并单测固化，此处固化为需求）。
- F5-4：三态在 `Item` 上仍以现有三字段承载（`hasDownloaded` / `hasDownloadedUnknown` / `hasTorrentRecord`），**不改接口字段名**；枚举已落地为 `DownloadService.LocalState { EXISTS, UNKNOWN, ABSENT }`，判定入口为 `resolveLocalState(...)`。
- F5-5：前端「已下载/未下载」筛选把 `UNKNOWN` 归入**已下载**（保持既有视图，已实现）；手动搜索的「只看未下载」同理（`isLocalPresent` 把存疑算作"已有"）。
- F5-6：每轮结束后统计 `EXISTS / ABSENT / UNKNOWN` 三个计数并透出（供验收与诊断）。预览已先行实现（`previewAni` 响应的 `localStateSummary`）。

| F6-5 ✅ | 互斥矩阵（实现与测试均以此为准） | 见下表；`AniLocksTest`（20 项）固化矩阵中每一条可观察语义 |

**F6-1 关键设计：读锁为什么用 try 而不是无条件等待**

写锁在下载期间会持有**分钟级**时间。若预览无条件等读锁，用户点开预览就会卡住几分钟——这比"读到稍旧的数据"糟糕得多（也正是 `3.2.31` 刚修完的"全局锁挂死"那一类体验问题的反面）。因此读路径统一走 `callWithTryRead(ani, timeout, supplier)`：只等 `DEFAULT_TRY_READ_MS = 300ms`，**等不到就不等、直接执行**，一致性由 `LocalStateCache` 的 TTL 快照兜底（缓存本身就是"上一次写完成后的结果"）。退化次数由 `getReadFallbackCount()` 观测。

两个必须遵守的约束（已写入 `AniLocks` 类注释）：

1. **持读锁的代码不得再取写锁**——`ReentrantReadWriteLock` 不允许读→写升级，会自锁死；持写锁再取读锁（降级）是允许的。
2. **只在外层入口加锁**——写锁可重入，但依赖重入会把锁边界散到各处。

**加锁顺序（禁止逆序）**：全局轮次锁 → 静默窗口 → 本订阅写锁 → 令牌桶 → 快照缓存。任何路径不得持有订阅锁的同时去等待全局轮次锁。

**F6-5 互斥矩阵**

| 入口 | 全局轮次锁 | 订阅锁 | 与周期轮并行 | 缓存 |
|---|---|---|---|---|
| 周期 RSS 更新 | 持有 | 写 | — | 读写 |
| 手动刷新（全部） | 抢占 / 排队（现状） | 写 | 否 | 读写 |
| 手动刷新（单订阅） | 不占（排队，`allowPreempt=false`） | 写 | 是（不同订阅） | 读写 |
| 预览 `previewAni` | 不占 | **读**（try，超时不持锁） | 是 | 只读 |
| 媒体库 `library` | 不占 | 无（仅缓存） | 是 | 只读 |
| 媒体库详情 `libraryDetail` | 不占 | **读**（try，超时不持锁） | 是 | 只读 |
| 手动搜索 `manualSearch` | 不占 | **读**（try，超时不持锁） | 是 | 只读 |
| 强制下载 / 重试失败项 / 删除种子 / 改名回写 | 不占 | 写 | 是（同订阅串行） | 写 + 失效 |
| 静默判定 `isQuiescent` | 不占 | 无 | 是 | 无 |

**为什么 `library` 不加订阅锁**：它是**批量**读路径，会遍历全部订阅。若逐个 `tryLock(300ms)`，多订阅同时下载时等待会线性叠加成秒级延迟；而它读到的只是"目录里有几集"的展示数据，半更新状态最多让计数短暂偏旧，不会像预览那样诱发"重复下载"这类写动作。一致性由 `LocalStateCache` 的 TTL 快照兜底（`scanOne` 内部走同一套快照）。

## 2. 边界与异常处理

### 2.1 网盘错误分类（必须区分，不能一律"存疑"）

| 场景 | 识别 | 处理 | 是否熔断 | 条目状态 |
|---|---|---|---|---|
| Token 失效 / 无权限 | 业务 `code` 属鉴权类（401/403 语义） | 全局告警（走既有 `NotificationUtil`），本轮所有订阅停止 Phase B | **是** | `UNKNOWN` |
| 目录不存在 | 业务错误文案含 not found / failed to get dir | 视为"确认没有" | 否 | `ABSENT` |
| 5xx / 502 / 503 / 504 / 超时 / 连接失败 | 既有 `isTransientOpenListFailure` | 按 `retryIdempotent` 重试，仍失败 → 计失败 | 累计到阈值才熔断 | `UNKNOWN` |
| 其余业务错误码 | `code != 200` 且非上述 | 记 WARN + 计入失败计数 | 累计到阈值才熔断 | `UNKNOWN` |
| 目录文件数超上限 | 列举结果 > `Config.cloudListMaxFiles`（默认 5000） | 截断 + 标 `complete=false` | 否 | `UNKNOWN` |

### 2.2 本地侧边界

| 场景 | 处理 |
|---|---|
| 下载器登录失败 | 整轮中止（现状保留），**不进入** Phase B |
| 改名失败 / 未打 `RENAME` 标签 | 该订阅 F4 判定不静默 → 本轮跳过；若走到 Phase B 则保持 `UNKNOWN`，**禁止判 `ABSENT`** |
| 种子记录存在但文件确实被删 | Phase B 判 `ABSENT`，**不自动删记录**，给"可清理"提示 |
| `rename=false` | **不产生存疑**：不发起网盘调用，按本地种子记录判定（有记录 → `EXISTS`，无记录 → `ABSENT`） |
| `fileExist=false` | 只影响下载去重策略，**不影响**「本地存在」展示（已实现，固化为需求） |
| 本地目录不存在 | 属"确认没有" → `ABSENT`，**不算**查询失败 |
| 本地目录不可读（权限） | 属"查询失败" → `UNKNOWN` |

### 2.3 调度与生命周期边界

| 场景 | 处理 |
|---|---|
| 单轮时长超过 `rssSleepMinutes` | 下一轮**顺延**，绝不并发叠加；WARN 提示"上轮未结束，跳过本轮" |
| 服务重启 | `RssJobStateStore` 恢复轮次状态；`LocalStateCache` 内存态清空，首轮全 Phase A（存疑），Phase B 逐步收敛；**不允许**重启后出现"否"的误判 |
| 订阅数极大（≥500） | 批次大小与预算按订阅数自适应；硬上限保护；前端显示"分批中" |
| 轮次进行中删除订阅 | 已提交子任务在检查点退出；缓存与 `DOWNLOAD_PATH_INDEX` 失效 |
| 手动刷新与周期轮重叠 | 沿用现状（全部刷新抢占；单订阅排队，`allowPreempt=false`） |
| 系统时钟跳变 | 批次 `nextBatchAt` 用 `System.nanoTime()` 计算间隔，避免 `currentTimeMillis` 回拨导致长睡 |
| 熔断期间用户手动刷新 | 仍然不发网盘请求；条目全部 `UNKNOWN`，并在响应文案中说明"网盘接口冷却中，本次仅按本地记录判定" |

## 3. 状态流转与并发控制方案

### 3.1 状态机

```
                      ┌──────────────────────────────┐
                      │  失效事件                     │
                      │  下载完成 / 改名完成 /         │
                      │  强制下载 / 删除种子 /         │
                      │  订阅配置或模板变更            │
                      └──────────────┬───────────────┘
                                     ▼
   ┌──────────────┐  Phase A（旧逻辑，0 次网盘调用）   ┌────────────┐
   │ 新一轮开始    │ ───────────────────────────────▶ │  UNKNOWN   │
   └──────────────┘   记录不存在 → 直接 ABSENT         │  （存疑）   │
         │                                            └─────┬──────┘
         │ rename=false：不发起网盘调用，                   │ Phase B（静默窗口 + 预算内，严格版列举）
         │ 有记录 → EXISTS，无记录 → ABSENT                 │
         │                          ┌───────────────────────┼─────────────────┐
         │                          ▼                       ▼                 ▼
         │                    ┌──────────┐           ┌──────────┐     ┌──────────────┐
         │                    │  EXISTS  │           │  ABSENT  │     │ 保持 UNKNOWN │
         │                    │ 真实存在  │           │ 确认不存在│     │ 校验失败/超预算│
         │                    │ +补种子记录│           │ 不删记录  │     │ /索引不完整   │
         │                    └──────────┘           └──────────┘     └──────────────┘
         └────────────────────────────────────────────────────────────────────▶ 直接判定（无 UNKNOWN）
```

**展示优先级**（前端）：`downloading`（有 `.pending`）> `UNKNOWN`（存疑）> `ABSENT`（否）> `EXISTS`（是）。

**筛选归属**：`EXISTS` 与 `UNKNOWN` 均归入「已下载」。

### 3.2 并发控制五层

| 层 | 机制 | 位置 | 作用 |
|---|---|---|---|
| L1 | 全局轮次锁 + 世代号 | `RssJobState.download` / `activeGeneration` | 同一时刻只有一轮；抢占靠世代号 |
| L2 | 静默窗口闸门 | `RssTask.isQuiescent()`（F4） | 后处理未完成不开新一轮 |
| L3 | 订阅级读写锁 | `AniLocks`（F6-1） | 同订阅串行、跨订阅并行；读不阻塞读 |
| L4 | 令牌桶 + 熔断 | `OpenListApi`（F7） | 网盘侧总速率与故障隔离 |
| L5 | 缓存单飞 + 失效钩子 | `LocalStateCache`（F2） | 同 key 只算一次；变更立即失效 |

**加锁顺序（必须自上而下，禁止逆序）**：L1 → L2 → L3（写）→ L4 → L5。任何路径不得持有 L3 的同时等待 L1。

### 3.3 竞态清单与对策

| 竞态 | 后果 | 对策 |
|---|---|---|
| 改名未完成 vs Phase B 判定 | 已下载被判 `ABSENT` → 重复下载 | F4 静默窗口 + 不静默则该订阅跳过 Phase B |
| 轮次副本 vs 实时订阅对象 | `enable`/`notDownload` 改动不生效 | F6-2 两处重新读取（提交前 + 子任务开头） |
| 订阅删除 vs 已提交子任务 | 对已删订阅执行下载 | 现状 `stillExists` 校验 + F6-1 写锁 |
| 缓存构建中 vs 失效事件 | 失效后又被旧构建结果写回 | 失效时递增 `version`，构建完成时校验 `version` 未变才写入 |
| 手动刷新 vs 周期轮 | 同一订阅并发下载 | F6-1 写锁（同订阅串行） |
| 预览 vs 下载写文件 | 读到半更新状态 | F6-1 读锁 + 缓存 TTL |
| 熔断冷却 vs 用户手动操作 | 长时间无数据 | 冷却中返回 `UNKNOWN` 并明确文案（2.3） |
| 多轮叠加 | 网盘调用翻倍 | 2.3「上轮未结束则跳过本轮」 |
